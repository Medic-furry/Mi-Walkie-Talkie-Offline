# App 侧握手协议与机型传输协议

本文根据本仓库 `V.01-BATE` 分支（修改版官方 App 的 apktool 工程）逐文件还原，未进行官方 APK 的新一轮逆向分析。

机型枚举依据官方 `lite/enums/DeviceTypeEnum`：

| 枚举 | 机型 | 设备类型值 |
|---|---|---:|
| DOLPHIN | 小米对讲机 1 代 | 1 |
| SHARK | 小米对讲机 2 代 | 4 |
| SEAL | 小米对讲机 1S | 5 |
| LITE | 小米对讲机 Lite | 36611 |

目前官方 App 实际使用了三套不同的通信协议：

- **Shark / Seal：** 使用 `0xFE01` 帧格式和 `0x4E21` 握手命令。
- **Dolphin：** 使用 MITALK 协议，通过 `MitalkProtos.Command` 封装消息。
- **Lite：** 使用独立的 blelib 命令封装，不经过前两种协议的帧格式。

本文主要记录官方 App 的发送侧实现，以及从代码中能够确认的协议结构。需要区分以下几种状态：

- **代码已确认：** 已从官方 APK 的代码中还原出对应逻辑。
- **本项目已实现：** 已移植到当前离线 App。
- **真机已验证：** 已有实际设备通信或功能测试结果。
- **待核对：** 静态代码分析已经得到部分结论，但仍缺少真机通信数据或完整协议字段信息。

标注 ⚠️ 的内容为尚待核对的部分。

## 1. 协议族 A：Shark(4) / Seal(5)

<text>**协议：** `0xFE01` 帧格式</text>

<text>**实现状态：** Shark 已实现并完成真机验证；Seal 已完成代码适配，尚未进行 1S 真机验证。</text>

### 1.1 GATT 结构

| 项目 | Shark | Seal |
|---|---|---|
| GATT 服务 UUID | `fdab` | `aee7` |
| 写入特征 | `aec7` | `aec7` |
| 通知特征 | `aec8` | `aec8` |
| 第二通知特征 | `feab` | `feab` |

Shark 和 Seal 使用相同的特征分工：`aec7` 用于写入，`aec8` 和 `feab` 用于接收通知。

### 1.2 帧格式

帧格式与本项目的 `FrameCodec.kt` 一致，所有 16 位字段均采用大端序。

```text
[0]     = 0xFE
[1]     = 0x01
[2..3]  = totalLen = 8 + payloadLen + 2
[4..5]  = cmd
[6..7]  = serial
[8..]   = protobuf payload
末尾    = CRC16（大端序 [hi, lo]）
```

字段说明：

| 字段 | 含义 |
|---|---|
| `0xFE 0x01` | 帧头 |
| `totalLen` | 帧长度字段，计算方式为 `8 + payloadLen + 2` |
| `cmd` | 命令码，例如 `0x4E21` |
| `serial` | 帧序号，范围 `0..0xFFFE`，逐帧递增 |
| `payload` | protobuf 序列化数据 |
| CRC16 | 覆盖此前全部字节，结果以大端序写入帧尾 |

### 1.3 握手请求

握手命令：

```text
cmd = 0x4E21
```

Payload 使用 `SEAL_Connect` 或 `SHARK_Connect`。两套消息的字段号一致，但 `deviceType` 由各自的官方 Builder 硬编码。

相关代码位置：

- Shark：`transport/g/SharkCommandHelper`
- Seal：`transport/f/SealCommandHelper`

| Field | 含义 | 官方取值 |
|---|---|---|
| 1 | version | `1` |
| 2 | connCode | `CONNECT = 1` |
| 3 | deviceId | 有存档时携带，无存档时省略 |
| 4 | deviceType | `4 = Shark` / `5 = Seal` |
| 5 | appMode | `OWN_APP = 0` |

`deviceId` 的处理逻辑：

官方 App 会检查 `ConnectionConfiguration.e()` 是否存在有效存档。如果存在，则通过 `parseInt` 转换并回显到握手请求的 field 3；如果不存在，则不发送该字段。

### 1.4 握手响应

响应命令：

```text
cmd = 0x4E22
```

响应中的 `connCode` 取值如下：

| 状态 | 数值 | 含义 |
|---|---:|---|
| DISCONNECT | 0 | 断开连接 |
| ALLOW | 4 | 允许连接 |
| REFUSE | 5 | 拒绝连接 |
| WAIT | 6 | 等待用户确认 |
| LOWPOWER | 7 | 电量过低 |
| BUSY | 12 | 设备忙 |

主要响应处理逻辑：

**ALLOW（4）**

设备在响应 field 3 中下发分配的 `deviceId`。App 收到后将其持久化，后续每次握手都会回显该 ID。

根据 Shark 真机测试，不携带 `deviceId` 或携带错误的 `deviceId` 时，设备会静默丢弃握手帧，不返回正常响应。

**REFUSE（5）**

响应 field 4 可以携带设备实际的 `deviceType`。

这一机制与机型识别有关：部分 Seal（1S）新固件只暴露 `fdab` 服务，单凭 GATT UUID 无法可靠地区分 Shark 和 Seal。

当 App 使用默认机型发起握手并收到 REFUSE，且响应 field 4 返回实际设备类型时，可以据此纠正机型并重试一次，同时按照设备 MAC 地址保存识别结果。

例如，issue #1 中记录的 fdab-only 1S 识别问题，响应中返回的设备类型为 `5`。

**WAIT（6）**

设备要求用户通过对讲机屏幕进行确认。此时连接流程不能直接按照普通 ALLOW 状态继续处理。

### 1.5 握手后的初始化序列

收到 ALLOW 后，官方 App 按照以下顺序初始化设备：

| 顺序 | 命令 | 用途 | 参数 |
|---|---|---|---|
| 1 | `0x4E23` | 设备参数查询 | `fullInquiry = 2` |
| 2 | `0x4E26` | 设备状态查询 | `ST_QUERY = 1` |
| 3 | `0x4E29` | 频道信息查询 | `chType = 2` |

### 1.6 一个容易混淆的字段：transMode 与 cmd

官方 `SendDataWrap` 的第三个参数名称为 `transMode`，但这个名称不能直接套用到所有设备协议。

在 Shark / Seal 场景中，该参数实际填入的是命令码 `cmd`，对应帧中的 `[4..5]`。

只有 MITALK 场景下，该位置才真正用于传输模式 `transMode`。

这也是本项目 `FrameCodec.kt` 中注明 `[4..5] 不是 transMode` 的原因。

## 2. 协议族 B：Dolphin（1 代）

<text>**协议：** MITALK</text>

<text>**还原状态：** 发送侧组帧和主要消息结构已从官方代码中还原；本项目尚未完成协议移植，部分字段和命令仍待核对。</text>

### 2.1 GATT 结构

Dolphin 使用的 GATT 服务 UUID 为：

```text
fee7
```

官方 `BtleCentralService` 对 `aee7`、`fdab` 和 `fee7` 三种服务采用同一套特征处理分支：

| 特征 | 用途 |
|---|---|
| `aec7` | 写入 |
| `aec8` | 通知 |
| `feab` | 第二通知 |

因此，Dolphin 虽然使用独立的 MITALK 消息协议，但底层 BLE 特征布局与 Shark / Seal 基本一致。

### 2.2 MITALK 帧格式

MITALK 的帧结构与 `0xFE01` 协议不同。根据 `node/transport/i` 中的组帧和拆帧逻辑逐行还原，其格式如下：

```text
[0]     = 0xFE
[1]     = 0x01
[2..3]  = totalLen = 8 + payloadLen
[4..5]  = msgId（普通命令）
          或 0 / 1（升级裸数据，对应 TransMode）
[6..7]  = 0x0001（静态常量）
[8..]   = MitalkProtos.Command 序列化数据
```

与 Shark / Seal 相比，MITALK 有三个关键差异：

1. 长度字段计算为 `8 + payloadLen`，不额外增加 CRC 所占的 2 字节。
2. `[6..7]` 使用固定值 `0x0001`，而不是逐帧递增的 serial。
3. 帧尾不追加 CRC16。

### 2.3 组帧逻辑的代码依据

组帧方法：

```text
i.a(II[BILTransMode)[B
```

其中 `deviceType == 1` 的分支具有以下特征：

- 长度字段只增加 `8`，其他分支则增加 `8 + 2`。
- `[6..7]` 取静态常量 `i.a = 1`。
- 其他分支使用 `i.b`，并在发送时递增。
- 发送方法仅在 `deviceType != 1` 时调用 `a([BI)` 追加 CRC16。

这些差异说明 Dolphin 并不是简单复用 Shark / Seal 的帧格式，而是使用独立的 MITALK 封装逻辑。

### 2.4 Payload 消息结构

MITALK 的 Payload 使用 `MitalkProtos.Command` 作为统一消息信封。

根据 getter 实际还原出的成员，当前能够确认的消息类型包括：

```text
ConnectQuery / ConnectResp

ParamQuery / ParamResp / ParamUpdate

StateQuery / StateResp

Control / Heartbeat

FileReq / FileResp / FilePack / UpdateResponse

LocationCtl / LocationSync / LogReq / TestReq / TestResp
```

大致可以分为以下几组：

| 消息组 | 主要用途 |
|---|---|
| Connect | 设备连接与握手 |
| Param | 参数查询、响应和更新 |
| State | 设备状态查询与响应 |
| Control | 控制命令与心跳 |
| File / Update | 固件文件传输与升级 |
| Location | 定位控制与同步 |
| Log / Test | 日志和测试相关功能 |

这里列出的是目前从官方 APK 中还原出的消息成员，并不代表所有成员的 protobuf 字段号已经确认。
